Verhalten ergänzen durch neue Handler — nicht durch Änderung bestehender

Ein neuer Handler in drei Schritten.
Klasse schreiben. Taggen. Testen.

Slack bei Refund, ERP-Sync, Loyalty-Buchung bei Capture — keine davon muss das Stripe-Modul anfassen. Sie hängen an einem Payment-Base-Event und laufen daneben.

Schritt 1 · HandlerInterface
final class SlackRefundNotifier
    implements HandlerInterface
{
    public function __construct(
        private SlackClient $slack
    ) {}

    public function handle(
        object $event, EventContext $ctx
    ): void {
        if (!$event instanceof
            PaymentRefundedEvent) return;

        $this->slack->post(sprintf(
            'Refund €%.2f auf %s',
            $event->getAmountCents() / 100,
            $event->getContract()->getOrderNumber()
        ));
    }
}

Acme\StripeNotifier\SlackRefundNotifier:

Schritt 3 · Unit-Test
public function testPostsToSlack(): void
{
    $slack = $this->createMock(
        SlackClient::class
    );
    $slack->expects($this->once())
        ->method('post')
        ->with($this->stringContains('€42.00'));

    (new SlackRefundNotifier($slack))->handle(
        new PaymentRefundedEvent(
            $contract, $this->refund(4200)
        ),
        new EventContext()
    );
}
Was Sie nicht tun sollten
  • Nicht oe_payments_stripe_wallet bearbeiten — koppelt das Feature an einen PSP.
  • PSP-unabhängige Events bevorzugen (PaymentRefundedEvent) statt Stripe-spezifischer — funktioniert dann auch für PayPal.
  • Stripe-SDK nicht direkt aufrufen — PaymentAdapterInterface injizieren.
