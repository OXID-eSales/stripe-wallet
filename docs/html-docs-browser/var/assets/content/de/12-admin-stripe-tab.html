Bestelldetails → Stripe-Tab

Ein Tab. Fünf Karten. Null DB-Snapshots.
Die Stripe-API ist die Quelle der Wahrheit.

Der Stripe-Tab im Admin-Bereich der Bestelldetails wird von OrderRefund gerendert — dem Controller für Capture, Refund, Autorisierungs-Stornierung und Reconciliation. Die Anzeige zieht bei jedem Aufruf Live-Daten von Stripe; die lokale DB ist Audit-Log, nicht Cache.

Was im Tab erscheint
  • Payment Details — Vertrags-ID, Bestell-ID, Zahlart, Transaction-ID mit Link ins Stripe-Dashboard, gebuchter Betrag, erstatteter Betrag
  • Transaktionsverlauf — aus getStripeTransactionHistory() — farbige Badges (Auth / Capture / Refund / Dispute)
  • Capture-Formular — für Manual-Capture-Verträge in AUTHORIZED; teilbar
  • Refund-Formular — für FULFILLED-Verträge mit Capture > 0; teilbar; prüft Restbetrag
  • Autorisierung stornieren — gibt nicht gebuchte Manual-Capture-Autorisierung frei
Speicher-Strategie · B+
  • Anzeige: Stripe-API — immer aktuell, deckt auch Dashboard-Aktionen ab
  • Audit-Log: oe_payments_transaction — eine Zeile pro über OXID ausgeführter Aktion
  • Self-Healing: reconcilePaymentState() läuft beim Anzeigen — korrigiert OXPAID, wenn Stripe succeeded zeigt, OXPAID aber leer ist
Controller-Dispatch · eine Aktion je Submit
class OrderActionDispatcher
{
    public function dispatch(
        Order $order, string $action, array $req
    ): void {
        match ($action) {
            'capture' => $this->dispatcher->dispatch(
                new StripeCaptureRequestEvent(
                    $order, $this->amount($req)
                )
            ),
            'refund' => $this->dispatcher->dispatch(
                new StripeRefundRequestEvent(
                    $order, $this->amount($req)
                )
            ),
            'cancel' => $this->dispatcher->dispatch(
                new StripeCancelAuthorizationRequestEvent(
                    $order
                )
            ),
        };
    }
}
