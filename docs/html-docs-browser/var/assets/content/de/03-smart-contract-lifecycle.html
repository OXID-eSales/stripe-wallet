Architektur · die Vertrags-Zustandsmaschine
„Bestellen“ erzeugt einen Vertrag, nicht direkt eine Bestellung

Der Smart-Contract-Lebenszyklus.
Acht Zustände. Drei Endzustände. Keine Unklarheiten.

Klassischer Checkout: Bestellen-Klick → Bestellung anlegen → bezahlen → Bestellung aktualisieren. Smart-Contract: Bestellen-Klick → Vertrag DRAFT → Bestellung NOT_FINISHED → Stripe-Session → Kunde zahlt → Vertrag wandert weiter → Bestellung wird finalisiert. Die Bestellnummer existiert vor dem Stripe-Redirect — Rückerstattungen und Audits laufen nie ins Leere.

Bedingungen am Vertrag
  • payment_authorized — wird gesetzt, sobald Stripe den PaymentIntent bestätigt
  • stock_reserved — der Reservierungs-Handler hängt an ContractCreatedEvent
  • fraud_check — optionaler Hookpunkt für Drittsysteme
Warum das für Stripe wichtig ist
  • Bestellnummer vor dem Redirect — wird an Stripe als metadata.order_id übergeben
  • BasketSnapshot unveränderlich als JSON in OXBASKETDATA gespeichert
  • OXORDERID bleibt NULL bis zum Status COMMITTED — keine Waisen-Bestellungen
  • Recovery-Flows hängen am Vertrag, nicht an der Bestellung — gleiches Vokabular für jeden PSP
Das Stripe-Modul mutiert nichts direkt. Es dispatcht Events — StripeCaptureRequestEvent, StripeRefundRequestEvent — und Payment-Base-Handler schalten den Vertragszustand weiter. Ein Pre-Commit-Grep-Guard lässt den Build scheitern, sobald ein Stripe-Controller direkt $contract->transitionTo() aufruft.
