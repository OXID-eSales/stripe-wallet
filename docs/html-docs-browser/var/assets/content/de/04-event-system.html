Architektur · Events & Handler
Durchgängig PSR-14 · getaggte Service-Discovery

8 Stripe-Events. 9 Handler.
Dispatchen, nicht mutieren.

Jede Aktion eines Stripe-Controllers nimmt denselben Weg: $dispatcher->dispatch($event). Handler mit dem Tag payment.event_handler werden vom EventListenerProvider automatisch eingesammelt und in Prioritätsreihenfolge aufgerufen. Eine neue Verhaltensweise hinzuzufügen heißt, einen neuen Handler zu registrieren — niemals einen Controller zu patchen.

Stripe-spezifische Events
  • StripeCheckoutSessionRequestEvent — startet Stripe Checkout
  • StripeCheckoutReturnEvent — Kunde kehrt von Stripe zurück
  • StripeCaptureRequestEvent — Admin bucht (unterstützt ?float $amount für Teil-Capture)
  • StripeRefundRequestEvent — Admin erstattet (unterstützt Teilerstattungen)
  • StripeCancelAuthorizationRequestEvent — gibt nicht gebuchte Autorisierung frei
  • StripePaymentExecuteEvent / StripePaymentReturnEvent
  • Stripe3DSRequiredEvent — SCA-Challenge erforderlich
Wiederverwendete Payment-Base-Events
  • ContractCreatedEvent · ContractTransitionedToPendingEvent
  • PaymentAuthorizedEvent · PaymentCapturedEvent · PaymentRefundedEvent
  • OrderCreatedEvent · OrderCompletedEvent
Handler-Registrierung · services.yaml
OxidEsales\Payments\Stripe\EventSystem\Handler\CaptureHandler:
    arguments:
        - '@OxidEsales\Payments\Stripe\Service\CaptureService'
        - '@Psr\Log\LoggerInterface'
    tags:
        - { name: payment.event_handler,
            event: StripeCaptureRequestEvent,
            priority: 100 }
Discovery zur Laufzeit
$provider = $container->get(
    EventListenerProvider::class
);
foreach ($provider->getListeners($evt) as $h) {
    $h->handle($evt, $context);
}
Handler-Prioritäten sind explizit. Reservierung läuft mit priority: 1000, Capture mit 100, Notifications mit 10. Reihenfolge ist Daten, kein Zufall. Ein Dritt-Handler bei priority: 50 braucht keine weiteren Änderungen.
