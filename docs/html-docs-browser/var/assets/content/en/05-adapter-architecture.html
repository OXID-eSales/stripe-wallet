Architecture · adapters
The seam between OXID, the Stripe SDK, and the contract spine

Three adapters do all the dirty work.
Everything testable. Nothing global.

Stripe's PHP SDK uses final classes and static config. OXID uses virtual parent classes and Registry::get(). Payment Base sits between them — constructor-injected DI all the way down. The adapter layer is the only place those three worlds meet.

StripeAdapter / LazyStripeAdapter

Wraps the Stripe SDK’s static config (API key, version) behind PaymentAdapterInterface. Lazy variant constructs the SDK client only on first call — safe to inject into long-lived services.

  • createCheckoutSession()
  • capturePaymentIntent()
  • refundCharge()
  • cancelPaymentIntent()
  • retrievePaymentIntent()
OxidShopAdapter

Implements ShopAdapterInterface. The only place Stripe code is allowed to touch oxNew(), Registry::getConfig(), or any other OXID global. Everywhere else uses this seam.

  • getOrderById($oxid): ?Order
  • getActiveBasket(): Basket
  • getActiveUser(): ?User
  • getViewConfig()
  • getShopUrl(): string
Helper trio

Adapter/Helper/ — small pure-function classes that translate between Stripe data shapes and OXID amounts. No state, fully testable.

  • PaymentIntentHelper — intent ↔ contract state mapping
  • RefundHelper — refundable validation, partial bookkeeping
  • CheckoutHelper — success/cancel URL construction, locale, line-items
Final classes are not enemies. Where the Stripe SDK ships final classes (e.g. \Stripe\Service\PaymentIntentService), the helper trio wraps the only methods we call. Tests inject real instances with mocked dependencies (the “final-class seam” pattern) — never createMock(FinalClass::class).
