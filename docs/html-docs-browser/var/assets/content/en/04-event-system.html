PSR-14 throughout · tagged-service handler discovery

8 Stripe events. 9 handlers.
Dispatch, don’t mutate.

Every action a Stripe controller takes goes through one path: $dispatcher->dispatch($event). Handlers tagged payment.event_handler are auto-collected by EventListenerProvider and called in priority order. Adding a new behaviour means registering a new handler — never patching a controller.

Stripe-specific events
  • StripeCheckoutSessionRequestEvent — initiates Stripe Checkout
  • StripeCheckoutReturnEvent — customer returns from Stripe
  • StripeCaptureRequestEvent — admin captures (supports ?float $amount for partial)
  • StripeRefundRequestEvent — admin refunds (supports partial)
  • StripeCancelAuthorizationRequestEvent — release uncaptured auth
  • StripePaymentExecuteEvent / StripePaymentReturnEvent
  • Stripe3DSRequiredEvent — SCA challenge required
Re-used Payment-Base events
  • ContractCreatedEvent · ContractTransitionedToPendingEvent
  • PaymentAuthorizedEvent · PaymentCapturedEvent · PaymentRefundedEvent
  • OrderCreatedEvent · OrderCompletedEvent
Handler registration · services.yaml
OxidEsales\Payments\Stripe\EventSystem\Handler\CaptureHandler:
    arguments:
        - '@OxidEsales\Payments\Stripe\Service\CaptureService'
        - '@Psr\Log\LoggerInterface'
    tags:
        - { name: payment.event_handler,
            event: StripeCaptureRequestEvent,
            priority: 100 }
Discovery at runtime
$provider = $container->get(
    EventListenerProvider::class
);
foreach ($provider->getListeners($evt) as $h) {
    $h->handle($evt, $context);
}
Handler priorities are explicit. Reservation runs at priority: 1000, capture at 100, notifications at 10. Order is data, not luck. Adding a third-party handler at priority: 50 doesn’t require touching anything else.
