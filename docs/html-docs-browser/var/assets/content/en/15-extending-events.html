Add behaviour by adding handlers, not by editing existing ones

A new handler in three steps.
Write a class. Tag it. Test it.

Slack on refund, ERP sync, loyalty allocation on capture — none of these touch the Stripe module. They subscribe to a Payment-Base event and run alongside.

Step 1 · HandlerInterface
final class SlackRefundNotifier
    implements HandlerInterface
{
    public function __construct(
        private SlackClient $slack
    ) {}

    public function handle(
        object $event, EventContext $ctx
    ): void {
        if (!$event instanceof
            PaymentRefundedEvent) return;

        $this->slack->post(sprintf(
            'Refund €%.2f on %s',
            $event->getAmountCents() / 100,
            $event->getContract()->getOrderNumber()
        ));
    }
}
Step 2 · services.yaml
Acme\StripeNotifier\SlackRefundNotifier:
    arguments: ['@Acme\Slack\SlackClient']
    tags:
        - { name: payment.event_handler,
            event: PaymentRefundedEvent,
            priority: 10 }
Step 3 · Unit test
public function testPostsToSlack(): void
{
    $slack = $this->createMock(
        SlackClient::class
    );
    $slack->expects($this->once())
        ->method('post')
        ->with($this->stringContains('€42.00'));

    (new SlackRefundNotifier($slack))->handle(
        new PaymentRefundedEvent(
            $contract, $this->refund(4200)
        ),
        new EventContext()
    );
}
What not to do
  • Don’t edit oe_payments_stripe_wallet — couples your feature to a single PSP.
  • Prefer PSP-agnostic events (PaymentRefundedEvent) over Stripe-specific ones — the handler then works for PayPal too.
  • Don’t call the Stripe SDK directly. Inject PaymentAdapterInterface.
