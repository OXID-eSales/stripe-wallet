## 1. Problem

On checkout step 3 (`cl=order`), a customer who selects the external Stripe Wallet method, goes to
the hosted payment page, and **returns via a fresh page load** finds the **Order now** button
disabled and cannot place the order.

Sprints 122/123 had already fixed the **bfcache / browser-Back** variant of this. The remaining,
untested cell was: **`blConfirmAGB` ON + fresh-load return + customer had already consented**. On
that render the apex `#checkAgbTop` re-renders unchecked, so `agb_validation_controller` disables the
button. The existing suite even treated this as *correct* (sprint-122 spec Case C).

## 2. Root cause

The customer's Terms acceptance — captured as `ord_agb=1` when the Checkout session was created — was
never persisted past the redirect. On return, the freshly rendered checkbox is unchecked → button
disabled.

## 3. Decision

**Restore prior consent** (Daniil, 2026-06-22, via clarifying question). Persist the consent
server-side for the checkout lifetime and re-apply it on return so `#checkAgbTop` renders/▸checks and
the button enables. We restore UI to reflect consent genuinely given; we do not fabricate new consent.
The apex checkbox markup is never modified (Sprint 101 edit boundary preserved).

## 5. The load-bearing invariant

The fix depends on `AGB_CONSENT_SESSION_KEY` staying **outside** `clearStripeSessionVariables()`. That
method runs inside `cleanupStaleCheckoutOnRender()` on the back-to-order render; the consent flag must
survive it, or the button breaks again. **Guarded by** the sentinel test
`testConsentSurvivesClearStripeSessionVariables`. Consent is instead cleared on `checkoutSuccess()`
(order placed) and `checkoutCancel()` (explicit cancel).

**Accepted residual edge:** browser-Back + abandon (no cancel) + new basket *in the same session* →
box pre-ticked. Bounded by clearing on success/cancel; widening to "basket changed" deferred (no
overengineering) unless legal requires it.
